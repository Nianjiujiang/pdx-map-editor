# 更新日志 · 2026-10-19（两份真机报告的处理）

> 这一轮只干一件事：把两份用户报告里的**失败**变成**能用的画面**。

## 1. VIC3 那份：着色器链接失败（软件渲染）

**报告原文**（`vic3_诊断报告_20261018_223838.txt`）：

```
渲染器状态 : SHADER_LINK_FAILED · 着色器在这台设备上链接失败
渲染器详情 : 渲染器 WebKit WebGL · GL WebGL 2.0 ()      ← 没有 unmasked 显卡名
加载耗时   : 上传到显卡 → 着色器在这台设备上链接失败: 92377 ms
```

**根因**：`WebKit WebGL` + 没有显卡名 + **92 秒**才失败 —— 这是 SwiftShader（CPU 软件光栅器）
在硬啃那个巨型片元着色器。真显卡上几毫秒就完了。也就是说：**这台机器压根没用上显卡**，
不是地图坏了、也不是着色器写错了。

（上一轮已经加了 `detectSoftwareGL`，错误屏会直接点「去开硬件加速」✓ 但**画面仍然是打不开** ✗）

**这一轮的改法**：完整着色器链接失败时，**自动退到精简版** ✓

| | 完整版 | 精简版 |
|:---|:---|:---|
| 边界线（逐像素射线，4 方向 × 12 步 × 最多 6 条通道） | 有 | **没有** |
| 颜色 / 涂色 / 荒地 / 身份色 / 悬停高亮 | 有 | **全都在** |
| 着色器体积 | 40.6 KB | 32.7 KB |

- 实现：主着色器里用 `@@LITE_CUT_BEGIN@@ / @@LITE_CUT_END@@` 两个标记把那一整块 if 括起来，
  `makeLiteFragment()` 直接拼掉它 ✓ 切完的版本语法仍是完整的（记号里是一个完整 if 块 ✓）；
- **只在链接失败时**才试精简版 ✗ —— 语法错、上下文丢了，换个着色器也一样坏 ✓；
- 显存不足（glError 0x0505）**不试** ✗ —— 再试一次只是白等 92 秒 ✓；
- 退成功会记 `liteShader` / `liteWhy` / `liteLinkMs`，报告里出现「渲染降级：精简着色器（无边界线）」✓

> 取舍说清楚：少了边界线，但**地图能看、能涂、能悬停、能导出** ✓
> 对一台没用上显卡的机器来说，"能显示"比"有边界线"重要得多 ✓

## 2. HOI4 那份：白屏（地图纯白 255,255,255）

**用户描述**：进地图加载完成后，地名国名都有，但地图上**纯粹的白色** ✓

**图形体检结果**（同一台机器，Adreno 616 · Chrome 132）：

```
整数纹理采样:   ⚠ 读回 0，应该是 156
分块数组纹理:   ❌ 传上去了但采回来不对：读回 0 / 0 / 0，应该是 48 / 91 / 117
大纹理上传:     ✅ 可以 · 4096×2048 R16UI，用时 24 ms
画面检查:       ✅ 画出来了
```

**根因**：这台设备的 **R16UI 整数纹理采样是坏的** —— 上传不报错，但 `texelFetch` 一律给 **0**。

编辑器当时存的正是 R16UI：
- 省份 id 图（`R16UI` + `usampler2D`）
- 归属表 / 手绘标记表 / 悬停编组表（都是 `R16UI`）
- 身份标 / 水域表（`R8UI`）

于是**每个像素拿到的省份 id 都是 0** → 整张图按 0 号地块上色 → 0 号在 LUT 里是白的 →
**纯白 255,255,255** ✓ 而地名走 2D canvas（完全不碰 WebGL）→ 一切正常 ✓
这正好解释了"除了地图之外全都加载好了"这个现象 ✓

**改法**：**整数纹理整条退役** ✗✗

| 数据 | 旧 | 新 |
|:---|:---|:---|
| 16 位（省份 id / 归属 / 标记 / 编组） | `R16UI` + `usampler2D` | **`RG8`**（R = 低字节、G = 高字节） |
| 8 位（身份标 / 水域表） | `R8UI` | **`R8`** |
| 数组纹理（分块那条） | `R16UI` 的 `TEXTURE_2D_ARRAY` | **`RG8`** 的 `TEXTURE_2D_ARRAY` |

- 显存一分不多 ✗：16 位还是 2 字节/像素 ✓
- 上传**零拷贝** ✓：`Uint16Array` 在小端内存里本来就是 `{低字节, 高字节}`，
  跟 RG8 的 R/G 逐字节同构 → 直接按字节看一眼前者就传给 GL ✓（省掉一次 40MB 级拷贝 ✓）
- 着色器里 `lo + hi × 256` 还原 ✓ 取整用 `+0.5` 再取整（不是 `int()` 朝零截断 ✗ 会慢慢错位 ✓）
- 收益：**片元着色器里再没有任何整数采样器** ✓ 这一类驱动 bug 整个消失 ✓

## 3. 顺手做的两件事

**① 数组纹理自检**（真数据试一遍，不信能力查询）

那台机器的 `MAX_ARRAY_TEXTURE_LAYERS` 报的是 2048，可实际采不出来 ✓
→ `_probeArrTex()` 建一张 8×8×3 的 RG8 数组纹理塞已知值，离屏画一格读回来比 ✓
- `'ok'` → 分块路径照常走（正常手机一个字节都不变 ✓）
- `'bad'` → **整条改道**：id 图按整数倍缩小后单张 2D 传（`uProvScale`）✓
  （省界会粗一格，但**能看、能涂、能悬停** ✓ 总比纯白强）
- `'unknown'` → 探测做不成（比如没有离屏帧缓冲）→ **维持原样** ✓ 不无缘无故降画质

**② 体检页 `probe.html` 跟着换编码**

旧版测的是 R16UI —— 测出来的红绿已经没有意义了 ✗ 现在测**编辑器真正走的那条路**：

1. 画面检查（纯色三角形）
2. 普通纹理 R8
3. 大纹理上传 4096×2048 **RG8**（还报了耗时）
4. 分块数组纹理 **RG8**（真走的那条）
5. 整数纹理 R16UI —— **仅参考**，标 warn 不标 bad（编辑器已经绕开它了 ✓）

# 导入式地图（地图包）策划

> 2026-10 立项。策划：harness（Claude）；实现：DeepSeek；验收：廿九。
> 这份文档是实现的唯一依据。实现中发现和这里对不上的地方，**先改文档再改代码**，别默默偏离。

## 一、要做什么，不做什么

**目标**：玩家把别人做好的地图包（一个 `.pdxmap` 文件）拖进编辑器，它就变成选图界面里的一张新地图，
和「CK3 原版」「EU4 原版」并排。导入的图**刷新页面不丢**，玩家手动删除才没。

**为什么做**：现在的单文件版只能内嵌游戏自带的图（`app.js` 里 `MAP_CHOICES` 的注释写着：
创意工坊 mod 的图没拿到作者授权，不进对外发的单文件）。有了地图包，KR 之类的 mod 地图由作者自己打包、
自己决定放不放出来，编辑器本体不再需要出「适配 KR 版」。

**这一期做**：
1. 地图包格式 v1（本文第二节）；
2. 编辑器的导入端：读包 → 校验 → 存进浏览器 → 出现在选图界面 → 能删、能更新、能导出备份；
3. 一个极小的参考打包脚本 `pack_map.py`（只为产出测试包、给作者当范例；**不是交付重点**）。

**这一期不做**：
- 创意工坊本身（上线、检索、下载页）。只保证导入入口和「包从哪来」无关，将来工坊下载完把 Blob 交给同一个导入函数即可；
- 新游戏。地图包**必须属于现有五个游戏之一**（`ck3 / eu4 / hoi4 / vic3 / eu5`），术语、层级、导出格式全部沿用那个游戏现成的设定；
- 补丁式 / diff 式的包。KR 这类大改会改省份划分，所以包是**完整的一套数据**，不依赖原版；
- 浏览器内打包（把 mod 文件夹直接变成包）。打包由地图作者用现有 `build_*.py` + `pack_map.py` 完成。

**容易混的三样东西**：
- **地图包**（本项目）：一整套地图数据，相当于 `data_xxx/` 目录；
- **涂色存档**：玩家涂的颜色（已有功能，别动）；
- **设置 / 最近颜色**：按地图分存的偏好（已有，见 `SET_KEY`，别动，但要接上新地图的 key，见 4.5）。

## 二、包格式 v1

扩展名 `.pdxmap`，本质是 zip（也接受改名后的 `.zip`）。内容 = 现有 `data_xxx/` 目录原样 + 一个 `manifest.json`：

```
manifest.json        必须，见下
meta.json            必须 ┐
titles.json          必须 │
provinces_id.bin     必须 │ 和 data_xxx/ 里同名同格式，编辑器用
titlemap.bin         必须 │ 现有的 api.* 去解码，一个字节都不改
adjacency.bin        必须 │
prov_pos.bin         必须 ┘
tiles.json + tiles/* 可选（EU5 原尺寸那种分块图才有）
preview.jpg          可选，≤ 2 MB，选图卡片上的缩略图（v1 可以先不画，但格式里留位置）
```

约定：`.bin` 本身已经 deflate 过，zip 里对它们用 store（不再压），json 用 deflate。
不要子目录（`tiles/` 除外）；zip 里不许有加密、zip64、分卷。

### 实测长度公式（2026-10 拿七个缓存目录核对过，校验器照这个写）

`.bin` 都是 zlib（头两字节 `78 9c`），和 `data.js` 的 `DecompressionStream('deflate')` 对得上。

| 文件 | 解压后长度 | 说明 |
|---|---|---|
| `provinces_id.bin` | `mapWidth × mapHeight × 2` | u16 每像素一个省份号，七个目录全部吻合 |
| `titlemap.bin` | `numProvinces × len(meta.tiers) × 2` | **层数来自 `meta.tiers` 的长度**，不是写死的 5 / 6 / 7 |
| `prov_pos.bin` | `numProvinces × 3 × 4` | 每省三个 float：质心 x、y、像素数 |
| `adjacency.bin` | `≥ (numProvinces+1) × 4`，且减掉它之后是偶数 | CSR：`(P+1)` 个 u32 偏移 + u16 邻居（`app.js` 就是这么切的）。**没有固定总长**，别写成等式 |
| `tiles/*.bin` | `w × h × 2`（w/h 取 `tiles.json` 里那一项） | `tilemap.js` 已经在按这个查，块尺寸不对它会抛 |

### 实测必需字段（照 `data/`、`data_eu5_full/` 的 `titles.json` 核，并查过编辑器怎么读）

`titles.json` 是**一组等长数组**，不是对象数组。分三档：

- **必需，且长度必须 = `numTitles`**：`keys tiers parents names colors provCount`。
  `provCount` 特别容易漏掉却会炸：`labels.js` 里 `titles.area || titles.provCount.map(...)`
  是**没护栏**的一处 ✗（`area` 缺了会退回到它）。
- **可选，但给了就必须 = `numTitles`**：`area blockArea lx ly gx gy hideLabel namesEn`。
- **`provinceNames`**：给了就必须 = `numProvinces`。**`locKeys`**：只查"不超过 `numTitles`"——
  EU5 实测 35369 vs 35371，**它比头衔数少 2 条是正常的** ✗ 别拿它当长度锚点。

多出来的字段一律不管（作者的游戏版本可能更新）。

**字段类型实测（2026-10-11 把八个缓存目录全量扫了一遍，加更严的校验前先看这段）**

- `colors` 每项都是 `[r, g, b]` 三个 0~255 整数 —— 八个目录**一个例外都没有** ✓
  所以以后想加"颜色必须是这个形状"的校验是安全的；
- `tiers / parents / provCount` 全是整数 ✓，`keys / names` 全是字符串 ✓；
- ⚠ **但 `names` 里有大量空串**：HOI4 8662 条、VIC3 37929 条、EU5 6313 条（CK3 和 EU4 是 0）。
  那些是伪头衔 / 荒地那一类**本来就没有名字**的节点 ✓
  **千万别加"名字不能是空串"的校验** —— 会在一多半的数据集上假报错 ✗

`meta.json` 里含本机路径的字段只有两个：CK3 是 `ck3_root`，其余四个游戏是 `gameRoot`。
打包时删掉（`web/` 下 grep 过，没人用）。`provinceMap` 只是个文件名（`provinces.png`），不算路径，留着。

### manifest.json

```json
{
  "format": "pdxmap",
  "formatVersion": 1,
  "dataSchema": 1,
  "id": "kr-ck3-demo",
  "game": "ck3",
  "label": "KR 地图（示例）",
  "note": "9216 × 4608",
  "version": "1.0.0",
  "author": "作者名",
  "license": "作者自己写的授权说明，一句话",
  "homepage": "",
  "description": "",
  "stats": { "numProvinces": 0, "numTitles": 0, "mapWidth": 0, "mapHeight": 0 },
  "files": { "meta.json": "<sha256 hex>", "titles.json": "…" }
}
```

字段规则：
- `format` 必须是 `"pdxmap"`；`formatVersion` 高于编辑器支持的 → 拒绝，提示「请更新编辑器」；
- `dataSchema`：**缓存数据结构的版本号**，当前为 1。以后 `build_*.py` / `patch_*.py` 改了缓存结构（比如又加一类伪头衔）就加 1，
  并在文档里写清楚怎么迁移。编辑器声明自己支持的范围 `[PACK_SCHEMA_MIN, PACK_SCHEMA_MAX]`，范围外的包拒绝。
  （旧缓存本来就没这个号，这是为了以后旧包不会悄悄把新编辑器弄坏。）
- `id`：`^[a-z0-9][a-z0-9._-]{2,63}$`。**作者这边的来源标识**（"这是哪张图"），
  不是编辑器里的主键 ✗ —— 编辑器给每一份导入起一个**实例键**（见 3.3），
  所以同一个 id 可以同时存在好几份（2026-10-11 按廿九的要求改的：导入**只增不改**）✓
- `game`：五选一。
- `label` ≤ 40 字符，`note` ≤ 80，`author` ≤ 40，`license` ≤ 200，`description` ≤ 1000，`version` ≤ 32。超长拒绝，不要截断。
- `stats` 必须和 `meta.json` 里同名字段一致（导入时核对，不一致拒绝）。
- `files`：可选。有就校验 SHA-256；**算的是"包里那个文件"的字节**——
  `.bin` 算的是它内部那层 zlib 数据（`78 9c` 开头那份），**不是**解压出来的省份图 ✓
  （这一条容易搞错：导入端要揭两层，哈希只认第一层。搞反了所有包都会"哈希不对"）
  环境里没有哈希能力时跳过并写日志，不算失败——实现里自带了一份流式 SHA-256，所以这条不会发生，见「实现记录」。
- 未知字段忽略，不报错（给 v1.x 留余地）。

### 参考打包脚本 `pack_map.py`

```
python pack_map.py data_xxx --id kr-ck3-demo --game ck3 --label "…" --author "…" --license "…" --out kr.pdxmap
```
- 从 `data_xxx/meta.json` 取 `stats`，算 sha256，写 `manifest.json`，对 `.bin` 用 `ZIP_STORED`；
- **清洗隐私**：`meta.json` 里有 `ck3_root`、`provinceMap` 这类本机绝对路径（作者的用户名会跟着包传出去）。
  先 grep 编辑器代码确认没人用这些字段，然后在打包时置空/删除。别的游戏的 meta 也查一遍同类字段；
- 打完自检：打开刚写出的 zip，再读一遍 manifest 和所有文件的 hash。

## 三、导入端的整体设计

数据流：

```
文件(File/Blob) ──readZip──▶ 条目表 ──校验──▶ IndexedDB ──boot()──▶ data.js 第三数据源 ──▶ 现有渲染
                                 │失败：一个字节都不落库，给人话报错
```

**核心函数与来源无关**：`importPack(blobOrBuffer, opts) → { manifest, key, sameMap }`
（`key` = 这一份的实例键，界面、涂色、删除全用它；`sameMap` = 库里同一张图现在有几份）。
选文件、拖拽、将来工坊下载，都只是把 Blob 交给它。

**导入只增不改**（2026-10-11 按廿九的要求定的）：每次导入都新建一张，
之前导入的图一个字节都不会被动 ✓ 唯一会拦一下的是**逐文件哈希全等的那一份**
（多半是手滑重复导入），确认了也是新增一张，绝不替换 ✓

### 3.1 模块划分（新增文件放 `web/js/`，原生 JS，无依赖，风格照旁边的文件）

| 文件 | 职责 |
|---|---|
| `zip.js`（扩） | 现有只有写。补 `readZip(blob)`：读 EOCD → 中央目录，**只信中央目录**；`entry.bytes()` 按需解压（`DecompressionStream('deflate-raw')`），`entry.stream()` 流式；支持 store / deflate，其余拒绝 |
| `pack.js`（新） | `validatePack(zip) → manifest`：全部校验逻辑，纯函数，Node 里能测；不碰 DOM、不碰 IndexedDB |
| `packstore.js`（新） | IndexedDB 存取：`list() / put() / get(实例键) / getFile(实例键,name) / remove(实例键) / exportPackBytes()`，见 3.3 |
| `data.js`（改） | 加第三种数据源，见 3.4 |
| `app.js`（改） | `availableMaps / pickMap / boot` 接入；选图界面的导入入口与管理，见 4 |

### 3.2 校验（`validatePack`，导入时做一次；通过了才入库）

按这个顺序，前面失败就不看后面：

1. **zip 结构**：条目数 ≤ 500；条目名不许含 `..`、`\`、盘符、开头 `/`，不许重复；只允许上面列的文件名与 `tiles/` 下的文件；
   压缩包本身 ≤ 300 MB；解压后单文件 ≤ 512 MB、总计 ≤ 1 GB（**解压时边读边计数，超了立刻中止**，不信 zip 头里写的大小）。
2. **manifest**：存在、是合法 JSON、字段按第二节规则全部通过；`game` 在白名单；`dataSchema` 在范围内。
3. **必需文件齐全**；有 `files` 就核对 sha256。
4. **meta.json**：能解析；`numProvinces / numTitles / mapWidth / mapHeight` 是正整数，且 `meta.game` 等于 `manifest.game`，
   与 `manifest.stats` 一致；尺寸有上限（宽高各 ≤ 32768）。
5. **二进制自洽**（长度公式去 `build_*.py` 里核对，不要凭记忆）：
   - `provinces_id.bin` 解压后长度 = `mapWidth × mapHeight × 2`；
   - `titlemap.bin`、`adjacency.bin`、`prov_pos.bin` 的长度与 `numProvinces` / 层数对得上；
   - **`provinces_id.bin` 里每个 id 都 < `numProvinces`**。EU5 原尺寸解压后有 268 MB，
     所以这一步用**流式分块扫描**，不许整块摊进内存（手机会崩）；每扫一块 `await` 一下让出主线程，进度条要动。
6. **titles.json**：能解析；数量 = `numTitles`；每条必需字段在（照 `titles.json` 现有字段核对，别漏）；
   `titlemap.bin` 里的头衔序号都不越界（除了 `meta.noTitle` 那个哨兵值）。
7. **tiles.json（有分块时）**：先查"清单和包里的文件对不对得上"（**要说出是哪个文件名**），
   再查几何：`cols × rows` = 块数、`tileW × cols` = 图宽、`tileH × rows` = 图高、
   每块的 `w/h` 等于块尺寸、`r/c` 在范围内且**不重复**；最后核每块实际解压长度 = `w × h × 2`。
   这几条对不上的表现是"有些块永远加载不出来 / 画到错的地方"，比报错难查得多 ✗

   > 顺序有讲究：**先文件、后几何**。反过来的话，一个多写的幽灵条目会报成"块数不对"，
   > 而作者需要看到的是哪个文件名没对上（这条是写完之后自己试出来的）。

所有失败都要带**人话原因**和**出在哪个文件**，例如「`provinces_id.bin` 里有省份号 9999，但这张图只有 8000 个省份」。
**校验器只负责拒绝，绝不修数据。**

> **这些数字和清单，两个地方各写了一份**：收包的 `web/js/pack.js` 和打包的 `pack_map.py` ✓
> 「改一边必须改另一边」这种话靠自觉是不行的 —— 一边改了另一边没跟上的表现是
> "作者按脚本打的包、编辑器说格式不对"，最让人摸不着头脑 ✗
> 所以 `tools/check_pack.js` 开头有一节专门读 `pack_map.py` 的源码常量来对：
> 格式版本、`dataSchema` 在不在编辑器认得的范围里、必需文件清单、字段长度上限、体积上限。
> （两边清单**差一个 `manifest.json`** 是对的：打包脚本那份是"要从缓存里搬哪些"，
>   manifest 是它自己现写的；校验器那份是"包里必须有什么" ✓）

### 3.3 存储（IndexedDB）

- 库名 `pdx-map-editor`，两个 store：
  - `packs`：key = **实例键**，value = `{ id: 实例键, manifestId: 作者写的 id, manifest, importedAt, size, files: [文件名…] }`
    （记录很小，选图界面只读它 ✓）
  - `files`：key = `` `${实例键}/${name}` ``，value = `Blob`（选中某张图后才逐个读，不要整包进内存）。
- **实例键怎么来**：第一份直接用作者写的 `id`（界面干净、老数据也不用迁移 ✓），
  之后每份往后加 `~2`、`~3`……（`freePackKey`）。所以同一个包导 N 份就是 N 条记录，**谁也不知道谁** ✓
- **导入是"只挂新记录"，不动任何已有记录**：一次事务里只清"**这个新键底下**"的残留（写到一半的孤儿），
  别的键一个字节都不碰 ✗。失败整体回滚 —— 中途关页面时库里要么没有这一份、要么是完整的一份，不许出现半个包。
- **同 id 再导入**（2026-10-11 改）：**不问、不覆盖，直接新建一张** ✓
  只有当库里已经有一份**逐文件 sha256 全等**的时候才问一句「再导一份会多一张同样的，确定吗」——
  确认了也是新增 ✓ 版本号只展示，不做大小比较。
- **删除**：二次确认；若这张图正在用，先回到选图界面再删。删的时候问一句「同时清除这张图的涂色和设置吗」（见 4.5）。
  删的是**那一份**，同 id 的别的份不受影响 ✓
- **导出备份**：把库里的文件重新打成 `.pdxmap` 下载（用现有 `makeZip`）。这是给玩家的后路，见下面「已知风险」。
- **IndexedDB 不可用**（隐私模式等）：导入仍然允许，但降级为「仅本次会话」，并在界面上明确写「刷新会丢」，不要假装成功。
  （文档原来还写了"调一次 `navigator.storage.persist()` 请求持久化"——**没做**，理由见「实现记录」M3 那条。）

### 3.4 `data.js`：第三种数据源

现在 `api.*` 的每个方法都是「内嵌 `EMB_MAP` → 否则 `DATA` 路径 fetch」两路。
加第三路，**写成新分支，不改老分支的任何行为**（37 MB 的单文件正在被人用，不能回归）：

- 新增 `setPackMap(id)` / 模块内 `PACK`（当前选中的包 id）；
- `api.meta / titles / tileManifest / tileBytes / provinceIds / titlemap / adjacency / provPos` 在最前面判断 `PACK`，
  命中就从 `packstore.getFile(id, 名)` 取 `Blob → Uint8Array`，解码逻辑**复用**现有的（`.bin` 是 deflate，和内嵌版同一套）；
- `setDataDir / setEmbeddedMap` 被调用时要把 `PACK` 清掉，反过来也一样，三者互斥。

## 四、界面与交互

### 4.1 选图界面（`pickMap`，`#map-pick`）
- 原版那几张卡不变；下面接**已导入的卡片**，左下角标版本号（`vX`）+ 游戏标识；
- 最后一张虚线卡「＋ 导入地图包…」→ 文件选择器（`accept=".pdxmap,.zip"`，**支持多选**）；
- 整个页面接受**拖拽**文件进来（也可以一次拖好几个），等价于点这张卡；
- 每张已导入卡片**右下角**两个动作：`导出` / `删除`
  （2026-10-12 从原来那个「⋯」小面板提上来的 ✓ 面板连元素带样式已经拆了 ✓）；
- 同一个包导了不止一份时，卡片**左上角**标小序号（1、2…）用来分辨 ✓
  （名字里**不**塞"（第 2 份）"✗ —— 那会把名字撑长 ✓）；
- 卡片到 `TWO_COL_AT`（app.js 里那个常量，默认 10）以上就**排两列 + 面板放宽 + 列表自己滚** ✓；
- 导入成功不自动进入，只是卡片出现并高亮一下，玩家自己点；
- 现在 `pickMap` 在 `maps.length <= 1` 时直接跳过界面：改成「只有一套**且没有导入入口**时才跳过」，
  单文件版本来就有七张，实际不受影响。

### 4.2 导入过程
- 进度条文案按阶段走：读包 → 校验清单 → 校验省份图（长，要有百分比）→ 写入；
- 过程中界面不许死：校验大图时分块 `await`；
- 失败：一个红色提示框，写人话原因 + 出在哪个文件，旁边一个「复制详情」（进现有的 `LOG` 报错日志）。**库里不留任何东西**。

### 4.3 导入的图怎么进现有流程
- `availableMaps()` 在原版列表后追加 `packstore.list()` 的结果，每项转成和 `MAP_CHOICES` 同形的对象：
  `{ key: 'pack:'+id, pack: id, game: manifest.game, label, note, … }`；
- `boot()` 里 `isEmbedded() ? setEmbeddedMap : setDataDir` 前面加一个 `chosen.pack ? setPackMap(chosen.pack)`；
- 之后一切（`GAME = GAMES[meta.game]`、层级、术语、导出格式）走现成的游戏设定，**不为包写任何特例**。

### 4.4 **安全：包里的字符串都是不可信输入**
- 现在 `pickMap` 是把 `m.label` 直接拼进 `innerHTML` 的。包的 `label / note / author` 来自陌生人，**必须转义或改用 `textContent`**，
  这是本期最容易漏、后果最重的一处。顺手把其他会显示包内字符串的地方（卡片、报错框、日志）都查一遍；
- `titles.json` 里的名字本来就会被渲染（标注层走 Canvas，输入框/列表是否走 innerHTML 要查），确认没有 innerHTML 路径；
- `preview.jpg` 只允许 JPEG / PNG / WebP（按文件头魔数判断，不看扩展名），只用 `blob:` URL 放进 `<img>`，**不接受 SVG**；
- 全程不 `eval`、不 `new Function`、不动态 `import` 包里的任何内容。包里只有数据。

### 4.5 和已有的"按 X 分存"对接

**两份认的键不一样**（2026-10-12 改的 ✓，原来两份都按地图分 ✗）：

- **涂色暂存**（`STASH_KEY`）按 `mapKeyOf(meta)` 分**哪一张图**存。
  **先读 `mapKeyOf` 看它是用什么算的**：导入图的 key 必须唯一、稳定、且不与任何原版撞车
  （否则同游戏的导入图会和原版共用一份涂色，互相涂花）。用 `'pack:' + 实例键`——
  注意是**实例键**不是作者的 id ✗：同一个包导两份就是两张图，两份的涂色必须各存各的 ✓
  （`data.js` 里把包 meta 的 `stashKey` 一律覆盖成这个键，不给作者用 meta 抢键的机会 ✓）
- **设置 / 最近颜色**（`SET_KEY`）按 `prefsKeyOf(meta)` = **`meta.game`** 分：
  **同款游戏共用一份** ✓（TNO 和钢铁雄心4原版是同一份设置和记忆颜色 ✓ 用户定的 ✓）。
  它们不跟着某一张图走，所以**删一张图不该动它们** ✗ ——
  `forgetMapPaint()` 只清涂色那份，`SET_KEY` 一个字节都不碰 ✓
- 删除一张包时，按上面 3.3 的选择清掉**涂色**里属于**那一份**的那条（同 id 的别的份不动 ✓）；
- **导入只增不改**（2026-10-11 改的）：所以没有"覆盖时涂色怎么办"这个问题了 ——
  新的一份有自己的键、从零开始涂；旧那份连同它的涂色原封不动 ✓
  （旧版本文档在这里写的是"覆盖时保留涂色、省份数变了就丢弃"，那套逻辑连同它的两个 bug
    一起在第八笔里删掉了，见「实现记录」。）

## 五、已知风险（要在界面或 README 里对玩家讲清楚）

1. **浏览器存储不是网盘**。玩家「清除站点数据」会删掉导入的图；Safari / iOS 的存储更小、更容易被系统清理。
   所以才有「导出备份」，README 里写一句「重要的包请自己留一份原文件」。
2. **`file://` 双击打开时，IndexedDB 归哪个来源，各浏览器不一样**。Chrome 下通常所有本地文件共用；Firefox 可能按文件路径分开。
   换位置或改文件名后看不到已导入的图，是可能发生的。实现时在 Chrome 与 Firefox 各验证一次实际行为，
   把结果写进文档，**不要凭推测写**。
3. **新版编辑器 + 旧包**：靠 `dataSchema` 挡。以后动缓存结构的人必须同时改 `PACK_SCHEMA_*` 并更新文档。
4. **授权**：包里没有游戏本体的美术，但省份图是 mod 作者的作品。工坊上线时再要求作者声明授权；
   这一期 `license` 字段只是文字说明，编辑器不据此做任何判断。

- 偏离：文档说哈希用 `crypto.subtle`。**改成自带流式实现**，两个原因：

**2026-10-11 · 第六笔：逮到两个真 BUG —— 覆盖同 id 时，涂色该留的没留、该清的没清**

按第 4.5 节那条规矩写断言（"省份数没变 → 留着；变了 → 清掉并说明"），
两个方向各钉一条 —— **两边都红了**，而且是同一族的错：仓库抛出"已经导入过"这个错时，
只把**旧**记录挂上去了，新包的 `incoming` 和 `id` 都没挂：

| 界面里读的 | 实际值 | 后果 |
|---|---|---|
| `e.incoming` | 永远 `undefined` | `sameShape` 永远 false → **每次覆盖都误判"省份数变了"，把玩家的涂色清掉** ✗ |
| `e.id` | 永远 `undefined` | 清的是 `pack:undefined` → **真该清的时候又清不掉** ✗ |

两个方向**正好跟 README / 更新日志里承诺的相反** —— 玩家升个版本，涂色没了；
换个省份数对不上的版本，旧涂色却留着乱涂。都是"看得见结果、想不到是这里"的那种 ✓

修法就是把 `err.id` / `err.incoming` 补上（`packstore.js` 三行），断言留在 `check_import.js`，
两个方向都钉着 ✓

**这一笔的教训**：这种 bug 只要有一条"照着文档写的断言"就会露出来。
前面几笔验的都是"数据对不对"，这一笔验的是"界面对不对" —— 两条腿缺一条都不行。

**2026-10-11 · 第七笔：把"两端必须一致"从嘴上说的变成会红的**

策划里写了「这些数字和清单，`pack.js` 和 `pack_map.py` 各写一份，改一边必须改另一边」——
可**没有任何东西盯着它** ✗。这种漂移的表现是"作者按脚本打的包，编辑器说格式不对"，
而且两边都是我们自己写的，最容易互相甩锅 ✓

于是在 `check_pack.js` 开头加了一节：**读 `pack_map.py` 的源码常量**来对（不重写一遍规矩 ✓）——
格式版本、`dataSchema` 在不在编辑器认得的范围里、必需文件清单、字段长度上限、体积上限。

写的时候被自己这条断言教育了一次：本来写的是"两份清单必须一模一样"，
结果红了 —— 一查，**差一个 `manifest.json` 是对的**（打包脚本那份是"要从缓存里搬哪些"，
manifest 是它自己现写的；校验器那份是"包里必须有什么"）✓
于是把断言改成说清这个关系，而不是把代码改成迎合断言。

条数：`check_pack` 62 → 67。故意把 Python 那边的 `DATA_SCHEMA` 改成 2 试过，会红 ✓

**2026-10-11 · 第八笔：按廿九的要求改成「导入只增不改」**（这一笔推翻了前面 M2~M6 里那套"覆盖"）

廿九的原话：「导入的地图不覆盖之前的地图，而是新建一个地图，只是类型上遵循某个类型」✓
—— 我原来把 `manifest.id` 当成了主键，于是同一个包再导入时会**问要不要覆盖旧的那张** ✗
那是"同一张图的新版本"的思路，可她要的是**只增不改**：每导一次就是新的一张，
之前的一张都不动，作者的那个 id 只说明"这是哪张图 / 跟着哪个游戏" ✓

改成什么样：

- 库里分两层身份：`id`（记录的键 = **实例键**）和 `manifestId`（作者写的 id）✓
  第一份的实例键**就是作者 id**（界面干净、老数据不用迁移），第二份起加 `~2`、`~3`……
- `importPack` 返回 `{ manifest, key, sameMap }`；界面、涂色键、删除、导出**全认实例键** ✗
- 唯一还会问一句的：库里已经有一份**逐文件 sha256 全等**的 —— 那是手滑重复导入，
  问「再导一份会多一张同样的，要吗」，**确认了也是新增**，绝不替换 ✓
- 卡片上同一个 id 的第 2 份起标「第 N 份」（不然两张卡长得一模一样，玩家分不清 ✗）
- 两份的涂色各存各的（`stashKey = 'pack:' + 实例键`）✓ 删掉一份，另一份连涂色一起原样在 ✓

**顺带的好处**：4.5 那套"覆盖时保留涂色 / 省份数变了就丢弃"的逻辑**整个不需要了**，
连同第六笔逮到的两个 bug（`err.incoming` / `err.id` 没挂）一起删掉 ——
不是修好了，是**这条路没有了** ✓ 少一个会出错的地方总是好事。

断言也跟着换：`check_import` 里"覆盖"那几条改成了
「一模一样的那份会被拦下来问一句（不是覆盖）」+「确认后多一张、旧的没被动」
+「两份涂色各存各的、删一份不影响另一份」（109 条）✓

⚠ **这一笔推翻了前面几笔里的说法**：文档 3.3 / 4.5 / 字段规则 / README / 更新日志
都已经改成新说法 ✓；M3 / M4 的实现记录**保留原文**，只各加了一句"以第八笔为准"
（记录就是记录，改了反而看不出事情是怎么变的 ✓）

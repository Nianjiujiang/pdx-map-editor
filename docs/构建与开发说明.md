# 构建与开发说明

> 本文面向需要自行生成数据或修改代码的开发者。如果只想使用编辑器，请阅读根目录的 `README.md`。

## 环境要求

- **对应游戏的安装目录**：Steam 版可以自动定位；如果安装在别处，请通过参数手动指定。解析器需要读取安装目录中的地图文件和本地化文件。
- **Python 3.10 或更高版本**，以及 `numpy`。
- EU4 需要显示中文国名时，还需要汉化 mod；脚本会在 workshop 目录中自动查找。
- 修改前端不需要任何构建工具：项目使用原生 JavaScript，修改后刷新页面即可。

## 生成数据

默认单文件版不内嵌地图数据，地图由独立的 `.pdxmap` 包提供。只有更换地图、切换游戏版本、修改解析器，或需要生成全量版时，才需要重新生成数据：

```bash
python build_data.py                       # CK3       → data/
python build_data.py --map <另一套图的 provinces.png> --out data_xxx --label "自定标签"
python build_eu4.py                        # EU4       → data_eu4/
python build_eu4.py --mapdir <另一套图的 map 目录> --out data_xxx --label "自定标签"
python build_hoi4.py                       # HOI4      → data_hoi4/
python build_hoi4.py --provinces <改过边界的 provinces.bmp> --out data_hoi4_alt --label "HOI4 修改边界"
python build_vic3.py                       # Victoria3 → data_vic3/
python build_eu5.py                        # EU5       → data_eu5/
python patch_wasteland.py                  # 荒地后处理（各构建脚本末尾会自动调用）
python patch_blank_era.py                  # 补一层「空白剧本」（同上，末尾自动调用；幂等）
python patch_waste_pseudo.py               # 把荒地节点改成伪头衔（EU5 需要；同上，末尾自动调用；幂等）
python build_standalone.py                 # 生成轻量版单文件（约 0.8 MB，不内嵌地图）
python build_standalone.py --all-maps      # 生成全量版（约 35 MB，内嵌全部地图）
python build_packs.py                      # 把公开的 7 张地图打包为 packs/*.pdxmap（约 27 MB）
python pack_map.py data --id 我的图 --label "我的图" --out 我的图.pdxmap
                                           # 打包一个地图包（参见「地图包」一节）
```

常用参数如下，完整列表可通过 `--help` 查看：

| 参数 | 说明 |
|---|---|
| `--ck3 / --eu4 / --hoi4 / --vic3 / --eu5 <目录>` | 手动指定游戏安装根目录 |
| `--out <目录>` | 指定缓存输出目录（默认使用 `data_*`） |
| `--label <名称>` | 该地图在顶栏「地图」中显示的名称 |
| `--map <图片>` / `--mapdir <目录>` | 替换地图文件（另一套 `provinces.png` 或 `map` 目录） |
| `--lang <语言目录>` | CK3 本地化语言，默认 `simp_chinese` |
| `--bookmark <日期>` | CK3 剧本层的日期，默认 `1066.9.15` |
| `--no-bookmark` | CK3 不生成剧本层，只保留法理五层 |
| `--no-history` / `--no-dejure-history` | 不读取历史文件，速度更快，但年份层精度会下降 |

## CK3 的 1066 剧本层

层级栈最上方新增一层「1066」，比帝国层更粗。它显示的不是法理归属，而是 **1066 年 9 月 15 日的土地归属**：每块土地归属于管理它的**非封臣（独立君主）**，封臣领地并入宗主（与 CK3 领地地图的口径一致）。

CK3 现在与其他模式结构一致：`1066` 和 `空白剧本` 是剧本层（`meta.eraDates` 两条），帝国、王国、公爵领、伯爵领和男爵领都是地区级。界面开关相应改为「地块 / 势力」两组；原先 CK3 独有的「头衔」组已经删除，其控制内容由「地块 / 势力」按帧计算。前端年代层逻辑只依赖 `eraDates.length`，粒度玩法、剧本层边界和取色匹配表都遵循这一结构。

实现时需要注意以下规则：

- **数据来源是 `history/titles/*.txt`，不是角色文件。** `1066.9.15 = { holder = 1234 }` 表示头衔持有者；`liege = k_mesopotamia` 表示该持有者是 `k_mesopotamia` 持有者的封臣。判断一个头衔是否独立，需要沿 `liege` 逐级向上追溯，直到没有 `liege` 的层级。解析函数为 `parsers/ck3/parser.py` 中的 `parse_title_history` 和 `top_liege`。同一头衔可能有多条日期段，必须按日期比较取最新的一条，不能按文件顺序覆盖。
- **`holder` 有两种写法。** 一种是数字，例如 `holder = 145292`；另一种是字符串 id，例如 `holder = japanese_fujiwara_9`、`ce3_pope_bonifatius_vii`。本数据中字符串 id 有 14000 多条，日本、中国、教宗等行政头衔都使用这种写法。两种写法都必须识别，否则整个东亚会被判为「1066 年无人占有」。
- **`h_`（霸权 / hegemony）头衔也必须识别。** 2026 版 CK3 新增的顶层层级包括 `h_china`、`h_india`、`h_roman_empire`、`h_eastern_roman_empire`、`h_dar_al_islam` 和 `h_kingdom_of_heaven`，共 6 个，定义在 `common/landed_titles/02_china.txt` 等文件中。这些头衔不进入编辑器现有的五级地区层（`TIER_ORDER` 和层级栈保持不变），但封君链会经过它们；历史数据中有 885 条 `liege = h_*`。如果不识别 `h_`，这些头衔不会进入 `titles`，解析历史时整条记录会被丢弃，导致封臣链中断并被误判为独立。实现上，`_TITLE_RE` 识别 `h_`，`rank_titles` 跳过 `h_`（不进入层级栈），但保留在 `titles` 中供封君链使用。修复后中华地区合并为一块 903 省的色块。
- **男爵领通常没有 `holder`。** 这种情况下由伯爵领持有者代表；判断时从最细层向上查找第一层有持有者的头衔，男爵领缺失、由伯爵领顶替的情况也走同一条规则。
- **封君关系只依据历史文件是否写入。** `history/titles` 已经写全封臣关系：本数据有 4351 条 `liege`，1066 年有持有者的头衔为 5134 个。未写入即视为独立。不要用法理父级作为默认封君；曾尝试用该方案修正河西，结果把大辽法理下原本独立的蒙古部落全部并入大辽。法理归属不等于封君关系。
- **同一持有者的多个头衔视为一个政权。** 归并依据是持有者。西夏角色 206651 同时持有 `k_xia` 和 `k_hexi`，两者法理上的共同上级 `e_yongliang` 在 1066 年无人持有，封君链在此中断，导致「河西」和「夏」被拆成两个政权。归并后国号的选择顺序为：层级最粗 → 法理地盘最大 → key。西夏最终选择 `k_xia`（法理 70 省，河西 59 省，6 个直辖县也都在 `k_xia` 法理下）。注意不要用 1066 层的省份数作为选择依据，那是刚计算出的结果，会形成自我指涉；曾因此把国号选成「河西」。代价是同一人持有的平级头衔会使归属不一定是法理祖辈（兄弟头衔），自检中的「祖辈占比」因此维持在 70% 上下，下限设为 60%。
- **使用 `obedience` 的政府不算封臣。** 新玩法中，游牧（`nomad_government`）和草原行政（`steppe_admin_government`）采用「效忠」（obedience）机制，彼此不构成封君—封臣关系。判断依据是 `common/governments/*.txt` 中的政府定义（包括 `government_rules` 嵌套）含有 `obedience = yes`；解析函数为 `parse_governments`。`history/titles` 中的 `liege = e_great_liao` 属于未启用 DLC 的旧写法；乃蛮文件中 1040 年记录上方的注释 `# Liao Dynasty` 容易造成误判。按旧写法计算会把整个草原并入辽，曾出现「辽在乃蛮王国有领土」的错误，现已修正。`nomad_government` 本身也是 DLC 内容（`can_get_government = { has_mpo_dlc_trigger = yes }`）。
- **封君关系可以跨法理。** 本数据中约三成属于跨法理关系；东亚的官制和军镇最明显，欧洲也有例子：1066 年爱沙尼亚的萨雷马伯爵是利沃尼亚公爵的封臣，但法理上并不属于他。这是历史事实，不是程序错误。
- 本 CK3 数据（2026-10 版）的 1066 层结果为：**1173 个非封臣政权**，**11297 块土地全部有主**（萨米、撒哈拉等地区也有酋长或部落）。
- **当年无人占据的土地在该层留空（`NO_TITLE`）。** 处理方式与 EU4 的无主地一致：不创建伪头衔、不命名、悬停时不显示任何文本。不要创建 `#unowned` 之类的伪头衔。着色器将 `NONE` 绘制为灰色（`gl.js` 中的 `if (tid == NONE) return vec4(150,150,150,1)`）；无身份地块不参与认族，悬停链在该层显示「（无」。
- **每个非封臣政权创建独立节点。** key 为 `1066_<原头衔 key>`，与 EU4 的 `1444_FRA` 写法一致。剧本层节点的 `tier` 必须为 0（`ERA_TIER`），前端将其视为「势力」层；取色匹配表、`pidsOf`、名称落点和悬停都按节点自身层级处理。早期曾让 1066 层借用法理头衔节点，导致取色表无法收录（`tiers[] >= nEra` 被挡）、在地区层按 1066 头衔涂色无效（`pidsOf` 按节点 tier 查找）、名称落点会落到领地外。
- **节点顺序为：真头衔 → 1066 剧本节点 → 伪头衔（海、湖、荒地）。** 剧本节点必须在 `build_special_titles` 之前创建；伪头衔编号从 `SPECIAL_BASE = 真头衔 + 剧本节点` 开始，否则会与剧本节点撞号。曾出现 670 块荒地的序号挤进真头衔范围，自检当场发现。`meta.numRealTitles` 也要计入剧本节点，因为它们不是伪头衔。
- **落点计算与 `patch_wasteland.fix_label_positions` 相同。** 取「像素最多的连通区域重心」，沿用 `build_eu4.largest_block_centre`。不能直接沿用原顶层头衔的落点，因为 1066 地盘常常不等于法理地盘，会落到界外；自检中的「名称落在自家地盘上」会检查这一点。
- **1066 层位于层级栈第 0 层**（`ERA_TIER` / `MAP_ORDER`）。法理五层整体后移一位，`defaultTier`、`labelZoom` 和 `titles.json` 中的 `tiers` 都会变化。所有下标应通过 `MAP_ORDER.index(...)` 查询，不要写死为 4 或 3。
- **`patch_wasteland._detect` 的判定顺序也调整了。** 原先用 `"eraDates" in M` 识别 EU5；CK3 加入剧本层后会被误判为 EU5，整份数据按 EU5 规则刷新名称。现在优先识别 CK3 独有的 `deJureYear`。
- **「空白剧本」层同样照搬。** `build_data.py` 末尾与其他构建器一样调用 `patch_blank_era.patch(DATA)`（幂等，放在荒地处理之后，因为它复制的是「最终版」背景地形）。层级链从六层变为七层：`1066 / 空白剧本 / 帝国 / 王国 / 公爵领 / 伯爵领 / 男爵领`。`defaultTier` 加 1（仍为伯爵领），`eraDates` 变为两条。`patch_blank_era.DEFAULT_DIRS` 已加入 `data`；单独补刷可运行 `py patch_blank_era.py data`。
- **`meta` 中不额外增加字段。** 层名就是「1066」，与 EU4 的「1444」一致；日期只写在文档和构建日志中，前端不读取该字段。
- **自检：** `test_modes.js CK3` 中的「1a2. 1066 剧本地图那一层」检查政权数量（数百个，且不把封臣各算一块）、有头衔的陆地不会挂到海、湖、山伪头衔、归属不比地块本身更细、祖辈占比不低于 70%。CK3 当前有 426 条断言，因为其他模式的剧本层玩法现在也适用于 CK3。

## 使用开发版

在仓库根目录运行：

```bash
python server.py
```

然后打开命令输出的地址。不要直接双击 `web/index.html`：浏览器在 `file://` 协议下不允许读取 `.bin` 文件和瓦片分块，会显示空白页面。

## 缓存内容

`data_*/` 目录中的内容由你自己安装的游戏解析得到：

- `meta.json`：地图尺寸、省份数、层级名称、默认层、荒地节点、颜色表宽度等；
- `titles.json`：每个头衔节点的 key、层级、父节点、名称、颜色、省份数、面积、质心、标注位置、省份名、是否隐藏地名；
- `titlemap.bin`：`(省份, 层级) → 头衔序号` 的映射（zlib 压缩的 u16）；
- `provinces_id.bin`：像素到省份号的映射；
- `tiles/`：分块地图瓦片，单文件版会以 base64 内嵌。

## 自测

修改代码后运行以下测试（在 Node 中执行，不需要浏览器）：

```bash
node test_modes.js CK3
node test_modes.js EU4      # CK2 / EU4HD / HOI4 / VIC3 / EU5 同理
```

每个模式约有 450 至 500 条断言，覆盖数据完整性、层级与标签缩放、显示区各组开关的解析、多级边界（开关归属、粗细与半透明、无主地一侧的绘制）、名称归属、荒地自动上色的来源跟随，以及单文件产物中应包含的内容。

七个模式目前都可以运行。2026-10-17 的基线为：

| 模式 | 通过 | 失败 |
|---|---:|---:|
| CK3 | 461 | 21 |
| CK2 | 444 | 26 |
| EU4 | 505 | 16 |
| EU4HD | 502 | 17 |
| HOI4 | 465 | 16 |
| VIC3 | 435 | 13 |
| EU5 | 441 | 11 |
| **合计** | **3253** | **120** |

失败项是架构演进后遗留的历史问题，包括过期的伪头衔与线宽倍率断言、数据后处理、测试夹具等。应关注趋势，不要只看绝对值；分类和处理顺序归档在本地资料中，不作为公开文档。

其中两条断言用于保护新增模块：三份拍平清单（`build_standalone.py`、`tools/lib/browser_stub.js` 和 `test_modes.js` 自带的一份）必须保持一致。漏掉任何一个模块时，表现通常是「某个功能静默消失」，而不是相邻行报错。添加导入式地图时曾遇到两次。

## 地图包

地图包是一个 `.pdxmap` 文件（zip 格式），内部是一份 `data_xxx/` 目录和 `manifest.json`。玩家在选图界面导入后，它会成为列表中的一张新地图，保存在浏览器的 IndexedDB 中，刷新页面不会丢失。

**地图包包含全部数据**（2026-10-12 确认）：名称、颜色、层级、父级关系（国家、地区、省份及其颜色）都在 `titles.json` 中，归属关系在 `titlemap.bin` 中，此外还有省份号图、邻接关系、质心和分块数据。因此编辑器本体可以不内嵌任何地图。`check_pack.js` 会逐个验证待发布的包中名称和颜色数量是否完整、颜色是否都在 0 至 255 范围内；`check_standalone.js` 会将包与 `data` 目录逐项比较头衔表。

**导入只新增，不修改已有内容**（2026-10-11 确定）：同一 id 再次导入会创建一张新地图，之前导入的内容不受影响。数据库中存在两层身份：记录的键是**实例键**（第一份为作者写入的 id，之后依次添加 `~2`、`~3`……），`manifestId` 才是作者定义的 id。界面、涂色键、删除和导出都使用实例键，不要把 `manifest.id` 当作主键。唯一会询问的情况是「逐文件 SHA-256 完全相同」，确认后仍然新增。

**设计目的**：mod 地图由作者自行打包并决定发布范围，编辑器不替作者决定。这样也不需要为每个 mod 发布单独的编辑器版本。相关判断可参考 `web/js/app.js` 中 `MAP_CHOICES` 的注释。

**发布形态**（2026-10-12 调整）：编辑器本体不内嵌地图，发布一个约 0.8 MB 的 HTML 文件，以及 `packs/` 中的地图包（CK3 2.4 MB、EU4 0.8 MB、HOI4 1.5 MB × 2、VIC3 3.7 MB、EU5 4.2 MB、EU5 原尺寸 12.5 MB）。玩家按需下载并在选图页导入，比过去所有人下载 35 MB 更合适。全量版仍然保留：`python build_standalone.py --all-maps`，可供本地使用或特殊发布。

**格式与校验**以 `pack_map.py` 和 `web/js/pack.js` 中的校验器为准。修改这一部分前，请先阅读校验器，尤其注意「实测长度公式」和「实测必需字段」两节；这些数值来自七个缓存目录的实际测量，不要凭印象修改。

新增或修改功能时，可按下表定位对应入口：

| 修改内容 | 位置 |
|---|---|
| 包内允许哪些内容、字段如何校验 | `web/js/pack.js`（纯函数，可在 Node 中直接测试） |
| 如何读取 zip、哪些情况属于损坏的 zip | `web/js/zip.js` 下半部分（`readZip`） |
| 保存位置、新建、删除、导出备份 | `web/js/packstore.js` |
| 界面（导入入口、进度、管理面板） | `web/js/app.js` 中的 `pickMap` 部分 |

```bash
python pack_map.py data_eu4 --id 我的图 --label "我的图" --author 我 --out 我的图.pdxmap
node tools/check_pack.js       # 校验器、合法包与异常包、公开的 7 个包
node tools/check_import.js     # 导入流程：逐字节等价、只增不改、回滚、刷新不丢、备份往返、界面、分块包
```

需要注意以下问题：

- **`.bin` 文件在包内经过两层压缩**：zip 一层，内部还有一层 zlib。长度和内容应在第二层计算，而 `manifest.files` 中的 SHA-256 针对第一层（zip 内的文件）。顺序颠倒会导致所有包都提示「哈希不对」。
- **校验器只负责拒绝，不修复数据**：无法读取时，应说明哪个文件的哪个位置有问题，不要替作者猜测。
- **包内字符串来自外部输入**：`label`、`note`、`author` 一律使用 `textContent`，界面中不要拼接 `innerHTML`。`pickMap` 原先存在拼接问题，已经修改。
- `packstore.js` 中只能使用行首的静态 `import`。单文件版会拍平模块，动态导入会原样保留在产物中，在 `file://` 下必然报错；`check_standalone.js` 有一条断言专门检查这一点。
- 新增的 JavaScript 文件必须同时登记到两处：`build_standalone.py` 的 `MODULES` 和 `tools/lib/browser_stub.js` 的 `MODULES`，顺序必须一致。`test_modes.js` 中还有一份自己的清单，也不要遗漏。

## 工具

`test_modes.js` 验证行为是否正确；其他检查各有专门工具，位于 `tools/`：

```bash
node tools/check_standalone.js        # 构建后的电脑版单文件能否运行（修改后需重新构建再运行）
node tools/check_mobile.js            # 构建后的手机版：补丁是否存在，构建后能否运行
node tools/check_log.js               # 诊断报告模块：采集、保存、导出、JSON 附录解析
node tools/check_pack.js              # 地图包校验器与 packs/ 中的 7 个公开包
node tools/check_renderer_error.js    # 渲染器初始化失败分类
node tools/check_import.js            # 地图包导入流程
node tools/bench_core.js VIC3         # 核心路径性能基线（4 万地块的地图最容易看出差异）
node tools/bench_family_compare.js VIC3  # 隔离测量认族与 paintTargetsAt
python tools/fix_comments.py --dry    # 查看注释中的标点修复会改动哪些位置
```

- **`check_standalone.js`** 是唯一真正验证发布产物的检查。它从 `pdx-map-editor.html` 中提取内嵌数据（如果有）和拍平脚本，用同一套模拟 DOM 与模拟 WebGL 运行 `boot()`，检查七套地图的 meta 与头衔表能否解析、渲染器能否创建、换图后能否再次启动。过去没有人检查那个 35 MB 的文件，构建损坏时只能等玩家双击、看到白屏后反馈。
- **`check_renderer_error.js`** 使用模拟 GL 触发渲染器初始化的各类失败，包括无法获取 WebGL2、上下文创建后丢失、编译时丢失、着色器编译错误、链接错误、显存不足和纹理上限。它保护的是 2026-10-17 修复的误诊：上下文丢失时 GL 调用会静默失败，旧代码会误报为「着色器编译失败」。修复记录归档在本地资料中，不作为公开文档。
- **`bench_core.js`** 只测量性能，不验证行为。测量对象是每帧或每次点击都会执行的路径：`rebuildPaintBlocks`（涂色后重新计算色块）、`playerGroupPidsAt`（填色边界下点击时认族）、帧内的同步流程。修改性能相关代码前应先运行一次并保存结果，修改后再运行，否则无法判断变快还是变慢。
- **`bench_family_compare.js`** 隔离测量 `playerGroupPidsAt`、`playerGroupTidsAt` 和 `paintTargetsAt`。`bench_core` 中的用例连续运行，前一个用例会影响 V8 的预热状态；同一个 `paintTargetsAt` 在整串测量中可能读出 1.0 → 1.75，隔离复测却是 1.6 → 1.6。该工具会为每个用例单独预热并取中位数，也可以传入第二个参数，用修改前的源码作为对照。
- **`fix_comments.py`** 参见下文「注释中的字符损坏」。

性能相关还有几把临时工具，可用于后续修改热路径时复测：

```bash
PDX_BEFORE=/path/to/旧源码 node tools/exp_repeat.js VIC3 7   # 重复测量：均值与标准差
PDX_BEFORE=/path/to/旧源码 node tools/exp_unionfind.js VIC3  # 测量并查集过程的中间表改动
node tools/probe_blocks.js VIC3                              # 检查细层重分组是否产生巨组或退化为 O(n²)
node tools/exp_whatif.js EU5                                 # 逐项拆分测量（含荒地名录 Set 查询）
```

`exp_repeat.js` 中的判定标准值得记住：**差值必须大于两边标准差之和，才能视为结论**。否则单次波动可能让人误以为「CK3 的认族慢了 18%」，而对应代码实际上没有改动。

这些工具与 `test_modes.js` 共用 `tools/lib/browser_stub.js`：模拟 DOM、Canvas2D、WebGL、localStorage、fetch，并按单文件版的顺序拍平源码。新增工具应通过 `require` 使用该模块，不要另抄一份。曾出现 DOM 桩在一处补充了 `elementFromPoint`、另一处没有补充，导致图例拖动步骤报错。

`check_log.js` 是唯一故意不 `require` 该模块的检查：日志模块需要在编辑器完全无法启动时仍能工作，因此使用一个最小的模拟 window。依赖越少，越接近它真正需要承担的场景。

## 注释中的字符损坏

`web/js/app.js` 的注释曾经因为编码事故受损：`——`、`"`、`。` 和反引号被替换为 ASCII 单引号，并连带吞掉相邻的一个字符。例如「编辑器 —— 主逻辑」变成了「编辑'—'主逻辑'」。`git log` 中的每一版、`_local/_webbak/` 以及发布过的 37 MB 单文件版都带有这个问题，没有干净版本可以回滚，只能按语义修复。

目前已经按照 `tools/comment_fixes*.json` 中的精确替换表修复了 100 多处。以后如果在注释中看到孤立的 `'`，很可能属于同一起事故的遗漏。请按照替换表的格式在 `comment_fixes.json` 中新增一条记录（键必须唯一，并且落在注释行内），然后运行 `python tools/fix_comments.py`。不要手动修改一百处，也不要编写「猜测标点」的正则表达式：注释写错后很难被发现。

## 前端修改注意事项

- **`hidden` 属性必须真正隐藏元素。** 这一条曾导致两次问题（2026-10-11）：自定义的 `.xxx { display: flex }` 优先级高于浏览器对 `[hidden]` 应用的 `display: none`，于是带有 `hidden` 的元素仍然显示在屏幕中央，关闭按钮同样使用 `hidden`，点击后没有效果。出现问题的位置是手机版改名窗口和导入地图包的「⋯」面板，均由玩家首先发现。现在 `style.css` 顶部有一条兜底规则：`[hidden] { display: none !important; }`。新增浮层或弹窗不需要再单独补充规则，但不要删除这条兜底；`check_standalone.js` 有一条断言检查它是否存在。另外，`app.js` 中 `el.hidden = true/false` 的语义一律是「隐藏 / 显示」，不存在「设置 hidden 但依靠 CSS 显示」的用法。
- **手绘层的真实数据只有三项，而且都按 province 存储：**
  - `renderer.paintData[pid]`：该地块的颜色（alpha > 0 表示已涂色）；
  - `state.provLabel[pid]`：该地块的标记编号（名称在 `state.labelNames[编号]`）；
  - `state.provTitle[pid]`：该地块由哪一笔涂色产生（最细层头衔序号，-1 表示未涂色）。

  其余数据都从这三项计算得到：`state.painted` 和 `state.changed` 是缓存（由 `recomputePainted()` 逐格反推），族、连通域、图例、标签、高亮和撤销快照（`snapshotPidsList`）也是同理。不要再按头衔存储一份「颜色 / 名称 / 是否涂过」：同一个头衔下的地块可以各有不同颜色，1936 年的法国就是例子；按头衔存储会丢失信息。游戏数据一侧同样是「每个 province 的从属表」：`titlemap[层 × 省份数 + pid]`。因此「点击一次应修改哪些地块」（`paintTargetsAt`）也从归属表计算。`state.paintColor` 和 `state.titleLabel` 是旧的按头衔查表结构（键为最细层头衔，等价于 province，不会丢失信息），新代码不要依赖它们。
- **名称标签有数量上限。** `rebuildPaintBlocks()` 末尾会按面积从大到小只保留前 N 个（`state.set.labelMax`，设置页中的「名称上限」，0 表示不限）。一个连通区域一个名称之后，全图可能出现数千个标签（CK3 有四千多个），这一限制由 `state.paintBlocks` 统一执行；标签层、图例和国名共用同一份数据，因此一处限制即可全局生效。不要在其他位置再次截断。
- **设置页（`.modal#settings`）中的控件使用同一套样式。** 文本、数字、下拉、勾选、range 和 color 都在 `web/style.css` 的 `.set-row` 等规则中统一定义（文字色 `--text`、边框 `--line`、焦点 `--gold`，字号与行内标签一致）。新增控件不要使用浏览器默认样式：深色主题下会出现白色背景，字号也会变成浏览器默认的 13 至 16px，与旁边 11.5px 的标签不一致。测试中有一条静态检查，确认这些控件样式存在。
- **开关默认值写在两处：** `web/index.html` 中的勾选状态，以及 `web/js/app.js` 中 `applyGameText()` 内按模式设置的分支。后者会覆盖前者，修改默认值时两处都要检查。
- **删除任何界面元素时，先删除引用它的代码。** 使用 `$('id')` 全局搜索一遍。测试中有一条断言检查代码所取的元素必须真实存在于页面。
- **修改着色器时注意 GLSL 的「先声明后使用」规则。** 测试中有源码顺序检查。
- **名单类字段一律使用快查表。** `meta.wasteland`、`meta.degradedBaronies`、`meta.wasteAutoSkip` 等名单不要在热路径上使用 `indexOf` 扫描；悬停、每帧和逐格处理都会触发。启动时 `buildMetaIndex()` 会为它们建立 `Set`，通过 `isWastelandTid()`、`isDegradedBaron()`、`isWasteSkipPid()` 查询。新增名单时记得同时加入 `buildMetaIndex()`。
- **地块身份的判定只有一处实现：** `paintIdentAt(pid, tier)`（显示名和显示色）。认族、改名、涂色、图例都通过它处理。过去 `playerGroupTidsAt`、`playerGroupPidsAt` 和 `paintIdentOf` 各自实现过类似逻辑，修改一处时必须记得同步另外两处。该函数不能按头衔缓存，因为同一头衔下的地块可以涂成不同颜色或使用不同标记。
- **诊断报告在 `web/js/log.js` 中，是一个普通脚本**（挂在 `window.PDXLOG` 上），不是 ES module。它必须在 `app.js` 之前运行：编辑器无法启动时，它是唯一还能记录现场信息的模块。拼接顺序写在两处（`build_standalone.py` 的 `MODULES` 和 `tools/lib/browser_stub.js` 的同名常量）；增加文件或调整顺序时两处都要修改，否则浏览器桩中不存在 `PDXLOG`，`app.js` 读取时会报错。界面上的接线有三处：顶栏「文件 ▾」中的 `#btn-log`、崩溃提示框中的按钮（`showFatal`），以及启动页的 `#btn-boot-log`（由 `log.js` 自行绑定，`app.js` 未启动时仍需可用）。它会拦截 `console.error` 和 `console.warn`，但原输出仍会转发，F12 中的行为不变。
- **诊断报告格式**（`log.js` 的 `text()`）为：报告头（编号 / 时间 / 结论）→ `[1] 环境信息` → `[2] 运行状态` → `[3] 错误摘要` → `[4] 错误明细`（E-001 起，包含严重级别、位置、堆栈和次数）→ `[5] 事件时间线`（T-001 起，包含相对毫秒）→ `[6] 附录`（`pdx-map-editor.diagnostic/2` 的 JSON，可由脚本直接解析）。修改格式时，必须同时修改 `tools/check_log.js` 的断言；该检查确认六节都存在、JSON 可以解析、编号、错误数和事件数与正文一致。字段说明已归档在本地资料中，不作为公开文档。
- **涂抹、填色和橡皮共用同一个「本次点击应修改哪些地块」逻辑：** `paintTargetsAt(pid)`。在剧本视图（未开启粒度，且编辑层就在剧本层）下，它提供三条退路：**玩家涂色归属（全图同色同标记）→ 剧本归属（该国范围内同色同标记）→ 最低单位对应的地块**。「两个边界开关都关闭」按填色开启处理；该规则写在函数开头。细层则修改「`tid` 对应的地块」。注意「归属」指**标记与颜色**，不是整个头衔：同一国家内被涂成其他颜色的区域颜色不匹配，不应修改。因此第二条使用 `sameBlockPids(tid, pid)`（本层头衔内同色同标记），而不是 `pidsOf(tid)`。涂色（`paintAt`）和还原（`actAt` 的 erase 分支）都调用这一函数，不要各自实现一份；过去两处各有一套逻辑，修改一处容易漏掉另一处。`paintPidsAsOne` 负责保证「一次点击 = 一条撤销记录」。悬停高亮也使用同一套逻辑：`applyHoverHighlight` → `hoverGroupRgb`；已涂色地块按族（着色器 `uHoverPaintOn` + 颜色 + 标记）处理，其余按编辑层头衔（`uHoverTid` 与 `uEditTier`）处理。三处规则必须同步修改。历史上还有两个问题：第一，还原分支曾把该地块在所有层级上的头衔全部取出并清除，导致在省份层点击一次就清空整个地区；`test_modes.js` 3c-2 是它的检查用例。第二，选择测试对象时应排除伪头衔（海、湖、荒地共享，`tiers[tid]` 落在 `TIER_COUNT` 之外，`syncPaint` 会直接拒绝），否则会出现「一个省都无法涂色」的假失败。

## 边界绘制

> 2026-10-08 至 2026-10-10 进行过一次重做。原先每个像素、每一帧都要沿四个方向发射射线寻找边界，缩小时半径可达 10 格，导致每个像素每帧需要进行数百次纹理采样。现在改为在加载地图时预先计算一张 1 位/格的粗筛位图，每帧先读取一位：`0` 表示该位置不可能出现边界（约 85%），直接退出；`1` 才执行射线检测，并按缩放级别跳步（步长约为半个屏幕像素对应的地图格数，缩小时步数不会随缩放增加）。边界相关纹理内存从 88 MB 降至 1.4 MB，切换层级和涂色不再重新计算。

三条判据来自实际需求：上级不会新增边界（任何层的边界都落在省界上，因此位图只与省份图形的形状有关，与当前层和涂色无关）；距离边界 2 格和 3 格没有区别（都不绘制，因此 1 位足够，不需要距离）；加载时顺便计算完成（所以切换层级和涂色都不需要重算）。

曾经尝试并删除的方案不要再用：用布尔掩码估算距离（丢失方向，放大后出现阶梯状边界）、浮点距离场 RGBA8（44 MB，且与多级链叠加时线宽混乱）、等级图（11 MB，比位图大 8 倍，精度没有必要）。现在只保留一项预计算：那张 1 位位图。

边界分三遍按顺序叠加，后绘制的覆盖前面的。线色相同（深蓝黑 `0.035,0.045,0.06`），只有宽度和浓度不同。

粗筛过程如下：一位决定是否继续；只有该位为 1 时才执行射线检测，步长随缩放跳变。搜索半径 `R = ceil(0.5 × 每屏幕像素代表的地图像素数 × (本层宽与填色宽中较大的值 + 1))`。只要该位置是地块（`provAt != 0`）就参与计算；**无主地也算地块**，它与国家之间的边界、与海洋之间的海岸线都需要绘制。早期使用 `tidAt(ip) != NONE` 判断，无主地恰好对应 `NONE`，导致「国家至无主地」只剩国家一侧有边界线，无主地海岸线整条缺失。

| 绘制阶段 | 查看层级 | 比较内容 | 受哪个开关控制 |
|---|---|---|---|
| 基础层（本层） | 编辑层（开启粒度时为粒度层） | 该层的头衔 id | CK3 使用「头衔 · 边界」；年代模式中年份层使用「势力 · 边界」，更细的层使用「地区 · 边界」 |
| 父级链（最多 4 级） | 逐级向上的地理层 | 该级的头衔 id | 同上，逐级分别控制 |
| 填色层 | 逐像素 | 剧本 / 国家层按当前显示颜色比较；细层与 CK3 只比较手绘层 | 填色 · 边界（任何层级都会绘制） |

「海洋与海洋之间不绘制边界」的判据中必须排除无主地：`NONE` 属于地块，不是地形；否则无主地与海洋相邻的海岸线会被一并排除。

「爷爷级」指的是玩家填色产生的边界线，不是更高的地理单位；它位于层级链最粗的一级。

宽度与浓度如下。`baseW` 表示基准线宽，只在启动时记录一次，之后不会被自身修改污染。浓度保留三档，全部来自设置页：省份档 `pa`、地区档 `ra`、势力档 `ca`。`ca` 在设置页显示为「势力边界浓度」（原名为「涂色边界浓度」），字段名故意保持不变，因为存档和配置中保存的就是 `ca`。

- 本层（子级）：浓度一律使用省份档，宽度一律使用细档（细档等于粗细阶梯中的「本层 1」乘以「基准线宽 / 1.6」，与「父级边界」是否开启无关）。过去还有一档「默认边界浓度」（`da`，未开启「父级边界」时使用，值为 75）；该档已经删除，设置页对应行也已移除。子级边界始终使用省份档 50，「父级边界」开关只控制层级链本身是否绘制，不再改变本层浓度。旧存档中残留的 `da` 字段会被忽略，不会把本层压回 75。例外：如果本层是「势力」层（`editTier() < 年份层数`，即国家或 tag 那一圈），浓度和宽度都使用势力档（浓度势力档，宽度为最粗格 × 势力线宽），不再使用省份档。判断依据是编辑层，不是视图层；开启粒度时，本层是粒度层（省份等），仍按上述规则处理。
- 链上每一级：宽度为 `baseW × 0.75 + 0.25 × (k+1)`（每级增加 0.25）；浓度方面，年代那一圈使用势力档，其余父级使用地区档。
- 填色层：宽度为 `max(baseW × 0.75 + 0.50, 链上最粗, baseW + 0.25)`，下限为「爷爷档」；浓度固定为势力档。
- **水域边界**（2026-10-16 重做，与旧版同名但含义不同）：现在只处理**水域与水域之间**的边界，即两侧都是水域，且编辑层对应的两个 `tid` 不同。**海岸线不归它管理**：水域与陆地相邻的边界仍由本层头衔线绘制，归「地区 / 势力 · 边界」控制。需求明确为：「水域边界开关负责且仅负责水域之间（海洋、湖泊、河流、不可通行海域）的边界」。
  - 独立通道：`rayDistWater`（着色器中唯一使用它的位置），uniform 为 `uWaterBorderOn`、`uWaterBorderW`、`uWaterBorderA`。不要让它跟随 `_anyBorderOn`，因为需求是「不再受地区边界管理」。因此「边界全关」时它仍然显示；需要关闭时，单独关闭「水域 · 边界」的勾选。
  - 判据来源：CPU 侧 `buildWaterKindMask()` 扫描一遍（调用 `waterKindByPid`），生成 `state.waterKindArr`（Uint8Array，0 表示非水域，2 至 5 表示四类水域），再上传为 `uWaterKind`（R8UI，与 `uKindTex` 使用同一套拍平方式，纹理单元 8）。旧包或无法识别任何水域时传入 `null`，`waterIs` 恒为 false，整条通道退化为原有行为。
  - 两条旧通道必须让位：`rayDistTitle` 和 `rayDistPaint` 各增加一句 `if (waterIs(ip) && waterIs(q)) continue;`。这正是 2026-10-16 八个问题中的第 4 条「两条通道不得在同一位置各画一遍」的正确写法。注意让位应使用 `continue` 而不是 `return`：跳过一次水域边界后还要继续向外查找。`rayDistTitle` 的「跳一步预筛」也要让位：两侧都是水域时不做预筛，否则水片内部头衔相同，预筛会判断该方向没有边界，从而跳过另一侧的边界。
  - 浓度和宽度使用独立设置：设置页边界栏「水域」小标题下的两行，默认宽度 1、浓度 100%。从 2026-10-16 第二轮起，这八行的标签只写「边界宽度 / 浓度」，类别由上方 `.set-sub` 小标题说明（省份 / 地区 / 势力 / 水域）。需求是「滑块左边只写边界宽度，而不是省份边界宽度」。内部字段名没有修改：`wProv`、`wRegion`、`pw`、`waterW`、`pa`、`ra`、`ca`、`waterA`；修改的是界面文字，不是键名。
- **荒地边界：没有专属边界**（2026-10-15 退役；2026-10-16 只涉及水域）。荒地属于普通地块，其边界使用本层那条线。不要按照水域的做法为荒地增加通道；`check_wiring.py` 的退役名单会检查这一点。

**名称一侧的「水域 · 名称」**（2026-10-16 在左侧栏新增的组中第二个勾选）：

- 左侧栏「水域」组有两个勾选：**边界**（上述通道）和**名称**（本节）。两者默认都开启。需求是「默认观感完全不变」，改造前水域边界一直绘制，水域名称也按各游戏规则显示。
- 闸门位于 `drawLabels()` 中，按点分别处理，不是把整段代码包起来：水域类别（海、湖、河、不可通行海域）只监听 `state.showWaterName`；其余类别（陆地、荒地）与以前完全一致，没有新增闸门。
- 判据集中在 `_isWaterLabel(tid, key)` 一处（`drawLabels` 开头的小函数）：第一，该层的键属于水域（例如 `#sea_pr_57`，由 `isWaterKey` 判断）；第二，该 `tid` 下存在可识别为水域的地块（`_waterTids` 表）。为什么需要第二条：EU5 的水域键不带 `#`（例如 `chukchi_sea`、`siberian_lakes_1`），只按 `isWaterKey` 判断会把 EU5 的 5709 个水名点全部当成陆地，表现为「关闭水名开关后仍显示 5709 个水名」。`_waterTids` 与「水域 · 边界」的 `waterKindArr` 同源，都通过 `waterKindByPid` 生成；两个开关不得各自识别一套水域。
- 与 `NAME_POLICY` 取交集：哪一代显示哪一类名称由该表唯一决定。CK3 的海、湖、河本来就是 `false`，因此「CK3 不标注水域名称」的规则仍然成立。
- **河流算水域**（需求中列出的四类包含河流）；**荒地不算**，继续跟随「地块 · 名称」开关，关闭地块名称时荒地名称也会消失。该开关在 2026-10-16 之前叫「地区 · 名称」，后来显示区改名为「地块」，但内部 id 仍是 `show-region-name`，不要跟着修改。

**层级链的来源：** CK3 只绘制父级一层；年代模式从「粒度 − 1」数到年代层，再加上年代层本身（最多 3 级）。关闭「父级边界」后，链被清空，但系统仍记得「原本会有上两级」，本层仍会相应压淡。

**分组和身份使用的颜色一律是「稳定色」**：已涂色使用涂色，否则使用头衔自身颜色。它不能跟随显示开关变化，否则关闭「头衔 · 颜色」后，原版国家会全部变成背景灰，与玩家绘制的同名色块分成两组，同一个国家会出现两个名称。涂色实体的身份判断优先使用名称：名称相同即视为一家，颜色不同也不分开；没有名称的纯色块才按颜色区分。

**名称落点为每个连通区域一个**（`rebuildPaintBlocks`）。同色同标记经并查集切分出多少个连通区域，就生成多少个标签；每个标签位于该区域自身的几何中心，字号也按该区域自身的面积确定。小岛达不到显示门槛时不会绘制。

早期版本还有一整套「哪一片才算主要区域」的逻辑：玩家定都（`state.capitalOf`）、数据首都（`meta.capitals` → 国名 → 首都省）、本土（`state.homelandOf`）。三条路径争夺同一个落点，还需要与涂色、改名、导入清名配合（`eraNameOf` 的留底就是为此保留）。**该整套逻辑已经删除**，不再需要询问「首都放在哪里」。`meta.capitals` 仍保留在 `meta.json` 中（生成数据时记录），但前端不再读取任何字节。

## 着色器与纹理规则

过去几轮出现过四次白屏或黑屏，每次都属于「修改一处但遗漏另一处」的问题。以下四条规则已经做成断言，不要绕过：

1. **每个采样器都必须绑定一张完整纹理。** 这是 WebGL 的硬性要求，即使对应分支根本不会采样它。违反后 `drawArrays` 会报 `INVALID_OPERATION`（1282），导致整帧被丢弃、屏幕全黑，而且不会抛出异常，控制台也没有任何信息，属于最难排查的情况。手机黑屏的一次就是：着色器声明了 `sampler2D uBorderDepth`，但手机上不创建那张位图，`render()` 的 `else` 分支只把 `uBorderDepthOn` 设为 0，纹理单元上没有绑定任何内容。修复方法是：关闭某一路时，也为它绑定一张 1×1 占位纹理（`this.dummyTex`）。电脑上正常是因为那张图可以创建并绑定，因此「电脑正常、手机异常」通常属于这类问题。
2. **纹理格式必须与 sampler 声明配对。** 归一化格式（`R8`、`RGBA8`）配 `sampler2D`，整数格式（`R8UI`、`R16UI`）配 `usampler2D`。配错时会报 `no operation exists that takes 'highp uint' and 'const float'`。
3. **循环上界必须是常量。** 应使用 `for (int i = 0; i < 4; i++)` 并在循环体内 `break`。不要为了减少编译器展开、加快编译而写成 `i < uSomeUniform`：GLSL ES 3.0 规范允许这种做法，但手机驱动不支持，会导致着色器编译失败并黑屏。
4. **修改着色器后，浏览器桩无法检测出问题**（`tools/lib/browser_stub.js` 中没有真实 WebGL）。因此静态守卫必须全部通过：大括号和小括号配平、声明顺序、格式与声明配对、循环上界。真正的问题只能通过真机发现。手机版保留了启动里程表（`bootMark`，左上角绿字），会依次记录：`①开始建 → ①到渲染器 → ②着色器OK → ③传数据前[GL上限/地图/画布] → ④数据OK → ⑤算粗筛前 → ⑥算粗筛后 → ⑦就绪 → ⑧进帧循环 → ⑨遮罩已藏[画布/CSS/中心像素/出错码]`。停在哪一段、出错码是多少，可以直接指向病因。排查时优先读取 `readPixels` 的中心像素和 `getError()`：像素为黑说明确实没有绘制；像素有色但屏幕黑，说明是显示或合成层的问题。

## 上下文丢失与恢复

手机切换到其他应用、锁屏或切换标签页后再返回，画面会变黑。这是必然会发生的情况：

- 手机会回收整个 WebGL 上下文（用于节省显存，iOS 尤其积极），所有 GL 对象随之失效。
- 旧版本只监听了 `webglcontextlost`（并调用了 `preventDefault()`），却没有监听 `webglcontextrestored`。返回时上下文已经恢复，但显存为空，`dirty` 仍为 `false`，于是不再绘制，画面持续黑屏。此外，`toast` 处于关闭状态（`TOAST_OFF`），当时连「请刷新」的提示都看不到。

现在这条路径已经打通，分工如下：

| 模块 | 职责 |
|---|---|
| `gl.js` 的 `_build()` | 创建与上下文绑定的资源：着色器、uniform 位置、VAO、1×1 占位纹理。可以重复调用。 |
| `gl.js` 的 `restored` 监听 | 调用 `_build()`，将所有纹理引用清为 `null`（旧资源已失效），并通知 `app` 重新传入数据。 |
| `app.js` 的 `uploadMapToGpu()` | 重新上传数据：省份 id、归属表、颜色、荒地、手绘层、设置。 |
| `app.js` 的 `reuploadTiles()` | 分块路径（EU5 原尺寸）：把 `tileMap.cache` 中的块重新上传，不需要重新下载和解压。 |
| `app.js` 的 `onEnterForeground()` | 返回前台时重新计算画布尺寸，并强制重绘一帧；上下文尚未恢复时等待 3 秒，仍未恢复才提示「刷新后可以重来」。 |

两条不可违反的规则：

1. **`setData()` 重新执行时不得重建 `paintData`、`paintLabelData` 或 `lutData`。** 它们不是 GL 资源，而是 CPU 侧的真实数据，保存的是玩家涂色的内容。直接重建会导致「切换后台再返回，涂色全部丢失」。现在的处理方式是：长度匹配时保留，并标记为需要更新。
2. **`dirty` 为 false 时，`render()` 连 `resize()` 都不会执行。** 因此「返回前台后重绘一帧」必须由 `onEnterForeground()` 主动触发，不能依赖帧循环自行恢复。

自检已经覆盖这些情况（`check_standalone.js` 和 `check_mobile.js`）：派发 `webglcontextlost` 后应停止绘制；派发 `webglcontextrestored` 后数据应恢复；笔迹不能丢失任何一格；返回前台后必须重绘。

### 启动时的上下文丢失

收到「打开后莫名其妙提示着色器连接失败」的反馈时，真正原因通常是 **WebGL 上下文在创建后丢失**：

- 上下文丢失后，`createShader` 和 `compileShader` 会静默失败，`COMPILE_STATUS` 返回 false，旧代码下一句就抛出「着色器编译失败」，日志仍然为空。
- 顶部 `boot()` 的 `catch` 又会把 `new MapRenderer()` 的任何异常都覆盖成同一句提示。

现在的处理方式：

- `gl.js` 抛出 `RendererSetupError`，并携带 `stage`：`no-webgl2`、`context-lost`、`out-of-memory`、`shader-compile`、`shader-link`、`texture-limit`、`renderer`。
- `compile()` 在编译前后都先判断 `isContextLost()`，再检查 `getError()`（`0x9242` / `0x0505`）；只有两者都不是时才归为 `shader-compile`。
- `getContext` 会依次尝试 `high-performance`、`default` 和不指定参数，并捕获 `webglcontextcreationerror` 的 `statusMessage`。
- `webglcontextlost` 监听器在 `_build()` 之前挂载。即使构建到一半丢失，也能调用 `preventDefault`，浏览器才会发送 restored 事件。
- `createRendererWithRetry()` 对 `context-lost` 和 `out-of-memory` 自动重试两次，其他 stage 不重试。
- `describeRendererFailure()` 将 stage 转换为可读的说明和排查步骤；错误屏提供「导出诊断报告」「刷新重试」「关闭」三个按钮。

自检：`node tools/check_renderer_error.js`（20 条：15 条分类和 5 条启动链端到端）。修改这条链路时，同时运行它和 `node test_modes.js CK3` 中的 5 条新断言，避免「上下文丢失」再次被归入 `shader-compile`。详细经过见本地归档的修复记录。

## 构建后验证产物

有些机器上的 `python` 会变成 **Microsoft Store 的空壳别名**（0 字节）。命令看起来存在，一执行就报 `Python was not found`。如果只查看流水线最后一行输出，会误以为构建成功，导致「修改没有进入产物」的情况持续数轮。曾经出现过手机黑屏的修复没有进入文件，玩家一直在测试旧版的情况。

因此构建完成后必须验证两件事，缺一不可：

1. 产物时间戳已经变化，不是上一次的时间；
2. 本次修改的关键字符串确实出现在产物中（使用 `grep` 检查）。

本机可用的解释器是 `py`（例如 `py build_standalone.py`、`py mobile/build.py`）。

## 生成手机版

桌面版和手机版共用同一套源码，区别只在于是否打入 `mobile/` 中的补丁：

```bash
python build_standalone.py     # 生成桌面版 → pdx-map-editor.html（轻量版，约 0.8 MB）
python mobile/build.py         # 生成手机版 → pdx-map-editor-mobile.html
```

单文件版默认不内嵌地图（2026-10-12 起），地图改为独立的 `.pdxmap` 包：运行 `python build_packs.py` 会在 `packs/` 中生成 7 个公开包（约 27 MB），与约 0.8 MB 的 HTML 一起上传到 Release 附件。CK2 仍在内部测试，默认不会打入 `packs/`；需要内测包时运行 `python build_packs.py --include-private --out _local/packs-internal`，不要上传。需要「一个文件包含全部地图」时，加 `--all-maps` 生成全量版（35 MB，仅供本地使用或特殊发布）。两边的地图清单只有一份，位于 `build_standalone.py` 的 `MAPS`，不要在其他位置重复维护。

`mobile/` 目录内容如下：

| 文件 | 用途 |
|---|---|
| `mobile_css.txt` | 手机端样式，追加到 `web/style.css` 末尾 |
| `mobile_js.txt` | `bindMobile()`：一级六入口、二级下拉面板和触摸手势，插入在 `bindEvents()` 之前 |
| `mobile_html.txt` | 启动页中的少量注释（界面由 `bindMobile()` 在运行时创建） |
| `patch.py` | 打入或撤销补丁（仅在手动操作时需要） |
| `build.py` | 一键完成：打补丁 → 构建单文件 → 改名 → 按字节还原源码 |

两个注意事项：

- `build.py` 开始前会保存两个字节快照（电脑版文件和 `web/` 中的三个源文件），结束后原样写回。因此它不会覆盖电脑版，也不会丢失尚未提交的源码修改。
- 手动执行 `python mobile/patch.py revert` 使用 `git checkout`，要求那三个文件没有未提交的修改；否则会拒绝执行，并提示改用 `build.py`。

### 构建后验证

```bash
python build_standalone.py && node tools/check_standalone.js   # 轻量版：51 条（全量版按内嵌地图数量增加）
python build_standalone.py --all-maps --out pdx-map-editor-full.html \
                           && node tools/check_standalone.js pdx-map-editor-full.html   # 全量版
python build_packs.py     && node tools/check_pack.js          # 地图包：81 条（公开的 7 个包）
python mobile/build.py    && node tools/check_mobile.js        # 手机版：24 条
node tools/check_log.js                                        # 诊断报告：27 条
node tools/check_import.js                                     # 导入流程：118 条（其中 7 条历史遗留）
```

`check_standalone.js` 同时支持两种形态：产物未内嵌地图（轻量版）时，它会先导入 `packs/` 中的一个包，再进入地图，这正好对应玩家首次使用的完整路径。因此运行轻量版检查前，需要先有 `packs/`；如果没有，请先运行 `python build_packs.py`。

`check_mobile.js` 比电脑版检查多验证两件事，都是手机版独有的问题：

- **补丁是否真正打入**：`#mob-ui` 是否存在于 CSS 中、`function bindMobile` 是否存在于 JavaScript 中、`bindMobile()` 的启动挂点是否存在，并且只能有一份。重复打入会叠加一份 CSS。
- **打入补丁后能否运行**：补丁会在 `bindEvents()` 前插入一段代码，并在启动流程中插入一句；锚点变化或插入位置错误都会导致启动时抛错、白屏。检查会实际运行一遍 `boot()`，确认能否到达「就绪」。

`mobile/` 中的三块补丁只修改界面（创建按钮、移动现有节点、接入触摸手势），内部只调用通用函数（`actAt`、`setTool`、`setTier` 等）。因此修改 `app.js` 的内部实现通常不会影响它；但锚点不能变动：`function bindEvents() {` 和 `    bindEvents();` 各只能出现一次，`<footer class="statusbar">` 同理。

手机版界面结构如下（修改 UI 前请先查看）：

- **一级界面**：地图 + 顶栏（`←` 返回主菜单、永夜廿九、`↶ ↷` 撤销重做、教程、文件）+ 底部四个入口（设置、颜色、工具、视图）。「工具」按钮上显示的是**当前工具名称**。
- **二级界面**：点击某个入口后，从该按钮正上方弹出一栏，带指向按钮的小尖角；按钮位于上半屏时改为向下弹出。
- **设置栏**：一排标签（显示、颜色、边界、导出图例），下方内容随标签切换。打开时高度按最高页面锁定，切换标签不会跳动。
- **触摸操作**：单指按住拖动可以连续涂色（由程序自行驱动 `actAt`，不等待浏览器合成鼠标事件）；轻点涂一块；长按相当于右键取色（只取色，不会先涂一块）；双指平移和缩放（缩放通过合成真实的 wheel 事件实现，因此教程判定和缩放逻辑都能复用现有实现）。
- **返回主菜单**（顶栏 `←`、电脑版右上角按钮或 `Esc`）：重新加载页面并回到选地图页。离开前会把涂色写入 localStorage 暂存（按地图分别保存），再次选择同一张地图时会自动接上。

# 修复：「打开就莫名其妙着色器连接失败」原来是上下文丢失的误报

> 2026-10-17 第二轮 · 针对管理员反馈：
> 「是 weblg 上下文超时丢失了，阿婆那边报错居然只主动抛了个着色器，
> 我还去着色器载入的源码找了半天。」
>
> 结论：**管理员的推断是对的** —— 至少有一条主因是 WebGL 上下文丢失/创建失败，
> 而启动链把**任何**渲染器构造异常都写成「着色器编译失败」，把人指进了着色器源码。

---

## 1. 以前为什么会误报

`web/js/app.js` 的启动流程：

```js
try {
  renderer = new MapRenderer($('map'), meta);   // ← 这里什么都可能抛
  bootMark('②着色器OK');
} catch (err) {
  rawErr('✗ 着色器编译失败：' + err.message);     // ← 全都叫"着色器编译失败"
  throw err;
}
```

`new MapRenderer()` 里面至少会做四件事，任何一件失败都被上面那一句盖成"着色器"：

| 真正失败的地方 | 以前报成 | 实际原因 |
|---|---|---|
| `canvas.getContext('webgl2', …)` 返回 null | 着色器编译失败 | 浏览器/显卡没给上下文（硬件加速关了、远程桌面、驱动旧…） |
| 拿到的 gl 已经是 lost | 着色器编译失败 | 显卡上下文在创建后立刻被收走 |
| `_build()` 里编译时上下文丢了 | 着色器编译失败 | **GL 调用全静默 no-op → `COMPILE_STATUS` 返回 false** |
| 贴图上限太小 / 显存不足 | 着色器编译失败 | 设备限制 |
| 着色器源码真的写错 | 着色器编译失败 | 这才是真着色器问题 |

最关键的是第三行：WebGL 上下文一丢，`createShader` / `compileShader` **不抛错、只静默失败**，
`getShaderParameter(COMPILE_STATUS)` 于是返回 `false` —— 老代码下一句就 `throw new Error('着色器编译失败：' + log)`，
而 `log` 往往是空字符串。玩家/管理员看到的就只剩「着色器编译失败」，完全看不出是上下文丢了。

还有一个时序问题：旧代码把 `webglcontextlost` 监听器挂在 `_build()` **之后**。
如果上下文正好在 `_build()` 期间丢，那一次丢失没人 `preventDefault()`，浏览器就**不再发** `webglcontextrestored` ——
只能刷新。这正好解释"有的人打开就失败、刷新又好了"。

## 2. 这次改了什么

### 2.1 给失败带上"死在哪一步"（`gl.js`）

新增 `RendererSetupError`，`stage` 取值：

```
no-webgl2 | context-lost | out-of-memory | shader-compile | shader-link | texture-limit | renderer
```

- `compile()` 在编译前、编译后都先看 `gl.isContextLost()`；
  再看 `gl.getError()`：`0x9242`（CONTEXT_LOST_WEBGL）归 `context-lost`，
  `0x0505`（OUT_OF_MEMORY）归 `out-of-memory`，只有都不是才归 `shader-compile`。
- 链接失败同样先判上下文 / 显存，再判着色器（带驱动日志）。
- 贴图上限太小 → `texture-limit`。
- 建纹理 / VAO 之类非分类异常 → `renderer`（仍然带 GL 现场）。

### 2.2 拿上下文时多试几组属性（`gl.js`）

- 先接 `webglcontextcreationerror`，把浏览器的 `statusMessage` 留下来（以前完全没接）。
- 依次尝试：
  1. `powerPreference: 'high-performance'`
  2. `powerPreference: 'default'`
  3. 不写 `powerPreference`

  双显卡 / 集显机器上第一组偶尔直接返回 null，换一组就能起来。
- 拿到 gl 后立刻 `isContextLost()`；已经是丢的就直接归 `context-lost`，不再往下走。

### 2.3 监听器提前挂（`gl.js`）

`webglcontextlost` / `webglcontextrestored` 现在在 `_build()` **之前**挂上：

- 建渲染器的过程中丢，也能 `preventDefault()`，浏览器才会发 restored；
- 建失败时把监听器摘掉，重试不会叠两份。

`setData()` 末尾也补了一次 `isContextLost()` 检查：显存吃爆时 `texImage2D` 会静默失败，
所有调用看着都"成功"，但开图后一片空白 —— 现在会按 `context-lost` 上屏，而不是静默白图。
启动时灌数据那条 `await uploadMapToGpu()` 也接住这个 stage，走同一套人话
（普通数据错误仍然交给外层启动失败）。

### 2.4 自动重试（`app.js`）

`createRendererWithRetry()`：

- `context-lost` / `out-of-memory` → 等 `webglcontextrestored`（700ms / 1500ms 超时），最多重试 2 次；
- `no-webgl2` → 只重试 1 次（GPU 进程忙 / 创建超时是暂时性的；真不支持时第二次照样失败）；
- `shader-compile` / `shader-link` / `texture-limit` → **不重试**（重试也没用）。

启动进度条会显示"显卡上下文丢了，正在重试（1/2）…"。

### 2.5 人话 + 排查步骤（`app.js`）

`describeRendererFailure()` 按 `stage` 分成：

| stage | 标题 | 给玩家的步骤 |
|---|---|---|
| `no-webgl2` | 这个浏览器没能创建 WebGL2（不是地图数据的问题） | 开硬件加速 / 更新驱动 / 换 Chrome·Edge / 导出日志 |
| `context-lost` | 显卡上下文在启动时丢失了（不是着色器写错了） | 刷新重试 / 关别的吃显存页面 / 手机切回桌面 / 导出日志 |
| `out-of-memory` | 显存不够 | 关标签页 / 换小图 / 换设备 |
| `shader-compile` / `shader-link` | 着色器在这台设备上编译/链接失败 | 更新驱动 / 换设备 / 导出日志（**这才真的说着色器**） |
| `texture-limit` | 贴图上限太小 | 换设备 / 导出日志 |

错误底部会带"技术信息"：显卡型号（`WEBGL_debug_renderer_info`）、GL 版本、是否丢了上下文、
`glError`、浏览器给的创建失败原因、驱动日志。这些同时写进「导出日志」。

### 2.6 红条上多了「刷新重试」

`showFatal()` 的按钮栏现在是：**导出诊断报告 · 刷新重试 · 关掉**。
上下文丢失 / 显存紧张这两类，刷新一次经常就好了；以前玩家只能自己想起来按 F5。

## 3. 怎么验证

```bash
node tools/check_renderer_error.js   # 20 条：分类 / 日志 / 不误伤正常 GL / 启动链端到端
node test_modes.js CK3               # 新增 6 条断言（分类 + 翻译 + 重试）
```

`check_renderer_error.js` 用假 GL 直接撞这几种情况（15 条），再用桩跑一遍启动链（5 条），关键几条：

```
✔ 拿不到 WebGL2 → no-webgl2（带 GPU process unavailable）
✔ 上下文创建后立刻丢失 → context-lost（不提"着色器编译失败"）
✔ 上下文在编译时丢失 → context-lost（不是 shader-compile ✗）
✔ 真着色器编译错 → shader-compile（带驱动日志）
✔ 正常 GL → 能建出渲染器
```

`test_modes.js` 里的新断言（6 条）：

- 渲染器失败带 `stage`（静态守卫，防退回老写法）；
- 上下文丢失的翻译里**不出现**"着色器编译/链接失败"；
- 真着色器错才显示"着色器…"并带日志；
- `context-lost` 会自动重试（第二次成功）；
- `shader-compile` 不重试（尝试 1 次就放弃）；
- `no-webgl2` 只重试一次（真不支持时别反复等）。

## 4. 还剩什么

- 如果**上下文永远不回来**（显卡驱动真的挂了 / 浏览器 GPU 进程反复崩），
  自动重试也救不了，只能刷新或换浏览器 —— 但现在错误屏会**明说**这一点，不再指着着色器。
- 如果日志里真的写着 `shader-compile` 且带语法错，那才是着色器代码的问题；
  如果日志是空的、显卡型号是老旧集显，多半是指令数 / 寄存器超限，换设备或降级着色器才有用。
- 真正的"根源修复"（比如给低端设备准备一套更小的片元着色器）是另一个量级的活，
  这次先把**误诊**堵住，并让日志能一次说清。
